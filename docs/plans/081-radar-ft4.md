# 081 — Radar: FT4 receive

## Decision

Add FT4 receive alongside FT8: same in-JVM decode lineage (the ft8_lib port in
`decode/ft8`), same HF contact log (new `mode` column), per-band panel rows
(`FT4-20`, `FT4-40`) mirroring the FT8 ones. Sub-second slot support lands in
`SlotAlignedScheduler` because FT4's grid is 7.5 s.

## Why

- FT4 is FT8's contest/DX sibling: 7.5 s slots (2x the QSO rate), ~3.1 dB less
  sensitive, and heavily used on 20 m/40 m sub-bands where FT8 saturates. For a
  receive-only DX ledger it doubles the sampling rate of the same bands.
- The decode stack shares everything hard with FT8 — 77-bit messages, CRC-14,
  LDPC(174,91), unpacking — all already ported and oracle-proven. The FT4 delta
  is the front end only: 4-GFSK at 48 ms symbols, a 4x4 sync pattern in 4 groups,
  2-bit Gray LLRs, and a 10-byte payload XOR whitening.
- Today's 40 m question ("is the band dead or the antenna deaf?") gets a second
  independent lens: FT4-40 samples the same band on a different sub-frequency.

## Architecture

- **`decode/ft8` grows an FT4 path.** `Ft4Protocol` tables extracted from
  ft8_lib `constants.c` exactly like `Ft8Protocol` was (script-extracted, pinned
  by structural self-checks, never hand-typed): `kFT4_Costas_pattern[4][4]` (+
  reversed variant if used by sync), `kFT4_Gray_map[4]`, `kFT4_XOR_sequence[10]`.
  Decoder gains an FT4 mode: waterfall at 0.048 s symbol period, sync search over
  4 groups at symbol offsets {0,33,66,99} (2 ramp symbols bracket the frame,
  data starts at symbol 1), 2-bit LLR extraction, then the SHARED `Ft8Code`
  LDPC/CRC and `Ft8Unpack` — with the payload XOR-dewhitened between CRC accept
  and unpack (that is where upstream applies it; the CRC arbitrates whitened
  bits).
- **Oracle discipline** (the spec-built-fixture rule): golden fixtures are WAVs
  generated by ft8_lib's own C `gen_ft8 -ft4` (checkout at `/home/sm/src/ft8_lib`,
  upstream 9fec6ca) with known messages at stepped SNRs, and the Java decoder
  must match `decode_ft8 -ft4` on the same files message-for-message. The C
  tools are the reference; the Java port is never tested against itself.
- **Scheduler**: `SlotAlignedScheduler.Cadence` gains a milliseconds-precision
  slot grid (int seconds today; FT4 needs 7500 ms UTC-aligned). Existing callers
  (15 s FT8, 120 s WSPR, NAVTEX/NDB windows) must be pinned unchanged by tests.
  FT4 capture ~6.5 s of the 7.5 s slot (transmission is 4.48 s + time-search
  budget); align window tightens accordingly. Exact capture/min-decodable
  seconds are MEASURED against the oracle (truncate WAVs until decode dies),
  not assumed.
- **Rx + persistence**: `Ft8RxProcess`/`Ft8Receiver` parameterized by mode
  (FT8/FT4 — capture length, decoder call, panel chip). `ft8_contact` gains
  `mode text NOT NULL DEFAULT 'FT8'` via its own changeset (additive column =
  new changeset per the schema rules); entity/repository/API expose it.
- **Config**: `radar.ft4.enabled` (default false), `radar.ft4.bands` =
  `14080000:20m:day,7047500:40m:night` (the standard FT4 dials), shared 96 k
  sample rate, `slot-every` default 2 (one capture per 15 s — same radio duty
  cycle as FT8 today). Panel rows `FT4-20`/`FT4-40` via the existing
  one-row-per-band doctrine.
- **UI**: FT4 history cards in `Receivers.tsx` (the FT8 card pattern), mode
  shown in the HF log view.

## Migration strategy

1. **PR1 — FT4 decode core.** `Ft4Protocol` (script-extracted tables + the
   extraction pinned by structural self-checks: sync/Gray bijections, XOR length),
   FT4 waterfall/sync/LLR in the decoder, payload dewhitening, reuse of
   `Ft8Code`/`Ft8Unpack`. Tests: self-checks, encode-decode round trip, and the
   oracle suite — committed `gen_ft8 -ft4` WAV fixtures decoded identically to
   `decode_ft8 -ft4` (messages, ±1 Hz freq, SNR sanity), including a truncation
   ladder pinning min-decodable capture length. Negative: an FT8 transmission in
   an FT4 decode window produces zero false accepts (CRC+LDPC guard), and vice
   versa.
2. **PR2 — slot machinery + persistence.** Milliseconds `Cadence` (existing
   cadences pinned by regression tests), mode-parameterized rx process and
   receiver, `mode` column changeset + entity/repo/API, `ft4Scheduler` bean +
   config, panel rows. Positive + negative scheduler-alignment tests (7.5 s grid
   lands on :00.0/:07.5; 15 s callers unmoved).
3. **PR3 — UI.** FT4 cards + mode in the HF log; frontend tests; full deploy
   (frontend build -> bootJar -> copy -> restart -> verified via API).
4. **Live acceptance.** Enable FT4-20 (day): >=1 real decode the same day (20 m
   FT4 is busy). FT4-40 evening comparison against today's FT8-40 silence —
   same antenna, second sub-band. Results recorded here.

## Risks

- The sub-second scheduler change touches every band scheduler: mitigated by
  pinning current cadences in tests before the change (15 s, 120 s), and by
  keeping `Cadence(int...)` as a compatibility constructor.
- FT4's tighter timing (6.5 s capture in a 7.5 s slot) leaves less late-start
  slack than FT8's 14-in-15: the align window and min-decodable threshold come
  from oracle measurements, and a missed slot costs 7.5 s, not 15.
- Waterfall geometry differs (more, shorter symbols): memory/CPU per slot is
  bounded by the shorter slot; verified by decoding fixtures at the target rate
  on the dev box before enabling live.
- Remote-path duty: FT4 windows ride the same rsptcp overlay slot as FT8 —
  slot-every=2 keeps the radio share identical, so no new arbiter pressure.
